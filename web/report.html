What Cullyard does, and how each part was checked

Cullyard is a local MCP server with a desk in the browser. An AI agent such as Claude Code or Antigravity reads the files in one folder, looks at and measures the photos, sorts everything into lanes, writes trimmed or resized copies, and can seal the sort log on Solana devnet. This page lists the evidence behind each of those claims.

Photo checks

File metadata cannot tell a sharp frame from a blurred one, so version 0.2.0 gives the agent the photos themselves and a set of measurements.

  • Pictures. contact_sheet returns one numbered JPEG grid of up to 16 photos, and preview_image returns one photo up to 1024 px. Both are MCP image results, so a vision model looks at the pixels.
  • Focus. Variance of the Laplacian on a contrast-stretched greyscale copy, per tile on a 4×4 grid; the sharpest tile counts. A frame is flagged soft under 40% of the set's median.
  • Exposure. Mean brightness and clipped shadows or highlights give dark and bright.
  • Bursts. A 64-bit difference hash and a 3×3 colour print must both match. The sharpest frame of a burst is kept; the rest are flagged duplicate.

Three mistakes were found and fixed while building this, each now covered by a test: the first version grouped every sample into one burst because the hash ignores colour; a dark frame also read as soft because darkness lowers edge contrast; and the dark frame's sensor noise ranked it sharpest of the set. Rank now puts clean frames first, and percentages are measured against the sharpest well-exposed frame.

Agent run

scripts/demo-agent.mjs starts the real server over stdio and calls tools the way an agent does, with a pause between calls so the desk can be watched. Steps, in order:

  1. scan_workspace on twelve sample files: seven JPG photos, one MP4, one MP3, one PDF, one CSV, one Markdown note.
  2. create_lane "Client docs".
  3. assess_photos, contact_sheet and preview_image on the top-ranked frame.
  4. Seven photo moves decided from the measurements: the top two clean frames to Picks, the other clean frames to Maybe, the soft, dark and duplicate frames to Rejects. Each move carries its reason.
  5. Four more moves for the PDF, CSV, video and song. The note stays in Inbox on purpose.
  6. resize_image on the top pick, IMG_2041.jpg, to 1200 px WebP. The original stays in place.
  7. trim_media on drone-pass.mp4 from 1 s to 4 s, stream copy, no re-encode.
  8. log_digest, seal_run, then verify_seal, which returned a match.

Every call and reply is in the agent transcript. Local paths in it were replaced with <workspace>.

Design choices

  • A workstation, not a landing page. The desk follows culling tools such as Photo Mechanic and Lightroom: dark neutral surfaces so photos read true, one amber accent for state, monospace for sizes and times.
  • Lanes are folders. What the agent sees, what the desk shows and what Explorer shows are the same thing, so nothing drifts between them.
  • Keyboard first. Select a card, press 1 to 9 to send it to a lane. Drag and drop works too, from Explorer onto any part of the desk.
  • Motion only where it explains something. Cards slide when a move happens; nothing loops for decoration. Reduced-motion settings turn transitions off.
  • Content without scripts. The site renders fully before JavaScript runs; the reveal animation is added only when scripts load.

Limits

  • The photo thresholds were tuned on generated test images, not on a real shoot yet. Flags are hints; the agent should still look at the contact sheet before rejecting anything.
  • A shallow-focus portrait or a deliberate low-key shot can be a keeper with "bad" numbers. The measurements cannot judge intent.
  • Image results were checked with the MCP SDK client and work in Claude Code. Whether Antigravity passes image results to its model was not tested.
  • Trim copies streams without re-encoding, so cuts land on the nearest keyframe and can be a fraction of a second off.
  • RAW previews depend on what the bundled image decoder can read. Some camera formats show size and kind only.
  • On the test machine, a trim through MCP took about 34 seconds end to end, mostly process start-up; FFmpeg itself finished in under 2 seconds.
  • Seals use devnet only. A devnet transaction shows that a hash existed at a time; it is not a legal record.
  • Tested on Windows 11 with Node 24. macOS and Linux should work but were not tested for this release.
